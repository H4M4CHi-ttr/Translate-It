# مشارکت در Translate It

این سند دستورالعمل‌هایی برای راه‌اندازی پروژه به صورت محلی و فرآیند اعمال تغییرات ارائه می‌دهد.

## نحوه‌ی مشارکت

ما از انواع مشارکت‌ها استقبال می‌کنیم! با وجود اینکه یک فرآیند پیشنهادی برای نظم بخشیدن به کارها داریم، **ما بیش از حد سخت‌گیر نیستیم**. مهم‌ترین چیز این است که مشارکت شما واضح و قابل فهم باشد.

### فرآیند پیشنهادی:

1. **فورک کردن پروژه**: یک کپی از پروژه برای خود بسازید.
2. **ایجاد برنچ (Branch)**: انتخاب یک نام واضح مثل `feature/new-button` یا `fix/typo` بسیار کمک‌کننده است.
3. **اعمال تغییرات**: قابلیت جدید خود را پیاده‌سازی یا باگ را رفع کنید.
4. **اعتبارسنجی**: بهتر است یک بررسی سریع (بخش [کیفیت کد](#کیفیت-کد-و-اعتبارسنجی)) انجام دهید تا از صحت عملکرد مطمئن شوید.
5. **ارسال Pull Request (PR)**:
   - یک عنوان واضح برای PR خود انتخاب کنید (ترجیحاً نام قابلیت یا اصلاحی که انجام داده‌اید).
   - به طور خلاصه توضیح دهید چه چیزی را تغییر داده‌اید.

*اگر در انجام هر یک از این مراحل با مشکل مواجه شدید نگران نباشید، ما در کل فرآیند به شما کمک خواهیم کرد!*

## 🛠 یادداشت‌های توسعه

### پیش‌نیازها

مطمئن شوید [**Node.js**](https://nodejs.org/) و [**pnpm**](https://pnpm.io/) نصب شده باشند. سپس، ریپازیتوری را کلون کرده و وابستگی‌ها را نصب کنید:

```bash
git clone https://github.com/Translate-It-App/Translate-It.git
cd Translate-It
pnpm install
```

### راه‌اندازی اولیه

پس از نصب وابستگی‌ها، دستور راه‌اندازی را اجرا کنید:

```bash
pnpm run setup
```

### ساخت برای توسعه

برای تولید فایل‌های افزونه جهت توسعه:

```bash
# ساخت برای هر دو مرورگر (به صورت موازی)
pnpm run build

# ساخت برای یک مرورگر خاص
pnpm run build:chrome
pnpm run build:firefox
```

برای مشاهده تغییرات در لحظه (Watch mode):

```bash
pnpm run watch:chrome
pnpm run watch:firefox
```

### کیفیت کد و اعتبارسنجی

#### بررسی کد (Linting)

```bash
# بررسی کدهای JS
pnpm run lint

# بررسی استایل‌های CSS
pnpm run lint:styles

# مرتب‌سازی کدها با Prettier
pnpm run format
```

#### اعتبارسنجی افزونه

```bash
# اعتبارسنجی هر دو مرورگر
pnpm run validate
```

#### گردش‌کار پیش از ارسال

پیش از ارسال تغییرات، بررسی جامع پیش از ارسال را اجرا کنید:

```bash
pnpm run pre-submit
```

این دستور لینت (JS و استایل‌ها) را اجرا کرده و افزونه را می‌سازد.

#### رفتار CI در PR

CI برای هر Pull Request هنگام باز شدن، بازگشایی یا به‌روزرسانی با کامیت‌های جدید اجرا می‌شود. ابتدا یک بررسی سبک Preflight انجام می‌شود:

- برای تغییرات فقط-docs/متادیتا اعتبارسنجی کامل اجرا نمی‌شود و فرایند سریع‌تر تمام می‌شود.
- تغییرات کد، پیکربندی، زمان اجرا یا ناشناخته، CI کامل (لینت، تست‌ها، ساخت، اعتبارسنجی) را اجرا می‌کنند.
- اگر PR قابل طبقه‌بندی نباشد (مثلاً مشکل API گیت‌هاب)، Preflight برای اطمینان CI کامل را اجرا می‌کند.
- فایل `docs/Changelog.md` را حذف یا تغییرنام ندهید — چون همراه افزونه بسته‌بندی می‌شود، Preflight در این حالت PR را مردود می‌کند.

Preflight کل تغییرات PR نسبت به `main` را ارزیابی می‌کند، نه فقط آخرین کامیت. اگر PR هم‌زمان شامل تغییرات کد یا پیکربندی باشد، حتی یک پوشِ فقط-docs هم CI کامل را اجرا می‌کند.

پوش‌های مرتبط به `main` همان بررسی‌های لینت، Stylelint، تست‌ها، ساخت و اعتبارسنجی را اجرا می‌کنند. پوش‌های فقط-docs/متادیتا Preflight را اجرا کرده و CI کامل برای آن‌ها اجرا نمی‌شود. بیلدهای کامل موفق روی `main` یک پیش‌انتشار (Pre-release) غلتان `Development Build` گیت‌هاب شامل ZIPهای توسعه کروم و فایرفاکس را به‌روز می‌کنند؛ این‌ها انتشار رسمی پایدار نیستند. انتشارهای رسمی گیت‌هاب (نسخه‌دار و پایدار) همچنان بسته‌های معتبر و دارای گواهی محسوب می‌شوند.

### بسته‌بندی برای انتشار

وقتی آماده‌ی ایجاد بسته‌های قابل انتشار هستید، از دستورهای زیر استفاده کنید.

**برای بسته‌بندی سورس‌کد:**

این دستور یک آرشیو `.zip` از فایل‌های سورس پروژه می‌سازد با نام `Source-vX.X.X.zip`.

```bash
pnpm run source
```

**برای ایجاد یک انتشار کامل:**

این دستور همه‌چیز را یکجا می‌سازد. آرشیو سورس‌کد و بسته‌های نهایی و قابل نصب `.zip` هر دو مرورگر را تولید می‌کند.

```bash
pnpm run publish
```

پس از اجرا، پوشه‌ی `dist/Publish` شامل موارد زیر خواهد بود:

- `Source-vX.X.X.zip`
- `Translate-It-vX.X.X-for-Chrome.zip`
- `Translate-It-vX.X.X-for-Firefox.zip`

### ایجاد انتشار رسمی (نگه‌دارندگان)

انتشارهای رسمی توسط GitHub Actions ساخته و منتشر می‌شوند، نه با انتشار دستی یک Release. گردش‌کار `Official Release` به صورت دستی شروع می‌شود و به ترتیب اجرا می‌کند: آماده‌سازی یا ازسرگیری امن تگ نسخه به‌علاوه Draft Release، ساخت و گواهی (attest) ZIPهای کروم/فایرفاکس، الصاق آن‌ها به درفت، راستی‌آزمایی تگ/Release/فایل‌ها، و فقط پس از آن انتشار درفت به عنوان آخرین انتشار پایدار.

پیش از شروع انتشار:

1. نسخه‌ی `version` در `package.json` را افزایش دهید و ورودی متناظر `docs/Changelog.md` را در `main` اضافه کنید (گردش‌کار تطابق تگ با نسخه‌ی بسته‌بندی‌شده را الزامی می‌کند).
2. در تب **Actions** ریپازیتوری، گردش‌کار **Official Release** را اجرا کرده و تگ نسخه را وارد کنید، مثلاً `v1.21.0`.

گردش‌کار fail-closed است: خطاهای پیش از مرحله‌ی نهایی انتشار، Release را به صورت درفت باقی می‌گذارند. تگ‌های نسخه‌ی موجود هرگز جابه‌جا یا بازنویسی نمی‌شوند، اما یک درفت ناتمامِ راستی‌آزمایی‌شده برای همان نسخه می‌تواند به جای تکثیر، از سر گرفته شود. وضعیت متناقض یا غیرمنتظره fail-closed است. درخواست نهایی انتشار مرز commit است: اگر همان درخواست به صورت مبهم شکست خورد، وضعیت Release را در گیت‌هاب به صورت دستی بررسی کنید.
